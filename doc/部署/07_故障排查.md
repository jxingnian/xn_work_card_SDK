# 故障排查

## 冷启动的出厂脚本提示

当前固定 rootfs 的 `/etc/init.d/S90autorun` 会尝试使用未随镜像提供的 `ubiattach` 挂载 `/app`，串口可能出现 `ubiattach: not found` 和 `/app` 挂载失败。该提示来自出厂 rootfs 的预留分区逻辑，不是 Work Card SDK 安装失败；SDK 验收以 `S91workcard_sdk`、`S92workcard_wifi`、`S93bluetooth_audio` 和 Demo 的实际状态为准。

## U-Boot 环境 CRC 损坏导致重启后无响应

如果启动日志出现 `Loading Environment from NAND... bad CRC`，随后直接停在 U-Boot `#`，原因已经确定为 NAND 环境区校验失败：`bootcmd` 和 `bootargs` 不存在，所以 U-Boot 不会自动加载内核。此故障发生在 Linux 之前，与 MQTT、媒体、WiFi 和蓝牙服务均无关。

只允许在 U-Boot `#` 提示符执行以下固定恢复命令：

```text
setenv bootargs 'mem=64m console=ttyAMA0,115200 clk_ignore_unused root=ubi0:ubifs rootfstype=ubifs rw ubi.mtd=3 mtdparts=nand:512K(boot),512K(env),4M(kernel),96M(rootfs) panic=5'
setenv bootcmd 'nand read 0x41000000 0x100000 0x400000; bootm 0x41000000'
saveenv
run bootcmd
```

`saveenv` 成功后必须再做一次软件重启和一次断电冷启动，两次都必须看到 `Loading Environment from NAND... OK`、自动读取 `0x100000` 的 4 MiB Kernel，并进入 Linux。禁止只执行 `nand read`/`bootm` 而不恢复 `bootargs`，否则内核缺少 UBI rootfs 参数，会停在 `Starting kernel` 且串口没有后续输出。

正式生产 rootfs 应由固件负责人根据真实 MTD/UBI 分区表修正或移除这段预留逻辑，不得在 SDK 现场安装脚本中擅自改动出厂分区。

## SDK 服务异常停止

`S91workcard_sdk` 由 `workcard-sdk-supervisor` 监督真实服务。真实服务异常退出后 supervisor 会记录 `exit_status` 并写入 `reboot.required` 保护标志，禁止在厂商媒体 HAL 状态未知时原地重新初始化；正常执行 `stop` 不会写入该标志。检查：

```sh
/etc/init.d/S91workcard_sdk status
tail -n 20 /tmp/workcard-sdk-service-exit.log
cat /run/workcard-sdk-supervisor.pid
cat /run/workcard-sdk-service.pid
ls -l /run/workcard-sdk/reboot.required
```

客户 Demo 收到“底层 SDK 服务连接已断开”后会有序释放媒体和云端连接。存在 `reboot.required` 时必须保留上述退出日志和 `/tmp/workcard-sdk-service.log`，然后执行整板冷启动；禁止连续强制杀进程或手工删除保护标志，强制 `SIGKILL` 可能使厂商媒体 HAL 只能通过冷启动释放。

## SDK 服务未连接

检查：

```sh
/etc/init.d/S91workcard_sdk status
ps | grep workcard-sdk-service
tail -n 100 /tmp/workcard-sdk-service.log
```

没有客户连接时，`/run/workcard-sdk/service.sock` 必须存在。第一版只允许一个客户独占连接，连接成功后服务会主动删除监听路径，因此 Demo 正在运行时看不到该 Socket 是正常行为。客户退出后服务释放媒体资源并重新创建监听路径。

第一版推荐在固定固件既有 root 业务用户下运行。判断已连接状态应同时检查 SDK 服务、客户应用进程和客户日志中的“底层 SDK 服务已连接”事件，不能在客户已连接后只检查 Socket 文件。

## 程序无法启动

```sh
file <程序>
readelf -l <程序> | grep interpreter
readelf -d <程序> | grep NEEDED
```

当前必须是 ARM EABI5、soft-float、解释器 `/lib/ld-musl-arm.so.1`。检查 `LD_LIBRARY_PATH=/opt/workcard-sdk/lib:/lib:/usr/lib`。

## 摄像头启动失败

检查：

- 固定固件和 SDK 是否匹配。
- SC2356 Sensor 库及配置是否完整。
- 是否有其他媒体程序占用 HAL。
- `config/hal_default.json` 和 `config/sc2356_stream.json` 是否存在。
- 服务工作目录是否为 `/opt/workcard-sdk`。

## WiFi 失败

```sh
wpa_cli -i wlan0 status
ifconfig wlan0
cat /tmp/workcard-wifi-reconfigure.log
```

密码必须为 8 到 63 字节，最多保存八个网络。API 成功不代表 DHCP 已完成，应继续查询状态。

## 蓝牙失败

```sh
/etc/init.d/S93bluetooth_audio status
test -c /dev/ttyAMA1
ps | grep '[r]tk_hciattach'
test -d /sys/class/bluetooth/hci0
test -d /sys/module/hci_uart
bluetoothctl --timeout 5 show
bluetoothctl --timeout 5 devices
cat /tmp/workcard-bluetooth-action.log
```

确认 `/sys/class/bluetooth/hci0` 和 `/sys/module/hci_uart` 均存在，并且 `rtk_hciattach`、D-Bus、BlueZ 和 BlueALSA 均已运行。当前只支持经典蓝牙和 A2DP Source；如果 `/sys/module/ble_soc` 存在，说明启动了被禁止的 WS73U 蓝牙路线。

如果 `rtk_hciattach` 日志连续出现 `OP_H5_SYNC Transmission timeout`、`Retransmission exhausts`，且 `/sys/class/bluetooth/hci0` 不存在，结论是 RTL8723DS 控制器没有响应 UART H5 握手。此时先检查硬件，不要反复重启服务：BL-M8723DS1 数据手册规定 34 脚 `BT_DIS#` 必须保持高电平，低电平会同时关闭蓝牙和 UART；同时必须确认主控 TX 接模组 RX、主控 RX 接模组 TX，H5 的 RTS/CTS 接线符合必联驱动说明。当前产品的核心板原理图和 UART1 pinmux 已完成确认，SDK 不再写入额外 GPIO 或 IOCFG 寄存器。

### UART1 帧错误和奇偶校验错误

本项目正式 UART 初始参数是 `115200 8E1`，不是 `8N1`。厂家 `Readme.txt` 的 UART 章节规定初始速率为 115200、协议为 H5，并规定主控 TX 接模组 RX、主控 RX 接模组 TX、主控 RTS 接模组 CTS；RTL8723D 允许模组 RTS 悬空，主控 CTS接地。核心板35/37脚分别是UART1_RXD/UART1_TXD，34脚是UART1_RTSN，33脚是UART1_CTSN。

量产接线必须是：

```text
核心板 35 UART1_RXD  <- 模组 P42 UART_TX
核心板 37 UART1_TXD  -> 模组 P43 UART_RX
核心板 34 UART1_RTSN -> 模组 P44 UART_CTS
模组 UART_RTS       -> NC（RTL8723D 官方说明）
核心板 33 UART1_CTSN -> GND
```

P44 直接接地不再作为正式接法。厂家配置在固件下载后启用主机硬件流控；缺少核心板33脚CTS接地时，初始化会固定失败在HCI Reset。板端已经确认UART1父时钟100 MHz、初始实际波特率115207、33/34/35/37复用值均为7。若日志在固件下载前出现H5同步超时，应先确认模组已经真正断电复位，不能只重启核心板而让模组继续停留在1.5 Mbps运行状态。

当前 HongOu Lite_P 开发板已经通过只读诊断确认 UART1 CTS/RTS/RX/TX 的 pinmux。出现同步故障时，不得继续修改扫描或后台代码，应依次确认模组 VDD33、VDIO、P34 `BT_DIS#`、模组是否完成冷复位，以及四线接法是否符合上表。

固定 rootfs 的 D-Bus 与 `bluetoothctl` 包含厂商构建机绝对路径和私有库版本要求，必须使用 SDK 安装的 `/opt/workcard-connectivity/dbus-system.conf`、`S93bluetooth_audio` 和 `/usr/bin/bluetoothctl` 包装器。包装器已固定 `DBUS_SYSTEM_BUS_ADDRESS`，不得依赖 SSH 会话中手工 `export`。不要删除 `/opt/bluealsa/bin/bluetoothctl.bin`。

如果直接执行 `bluetoothctl` 出现 `dbus_connection_get_object_path_data` 断言，表示包装器未正确安装或版本过旧，应重新执行 `./scripts/install_target.sh`。禁止通过全局修改 `/etc/profile` 规避该问题。

扫描结果只允许包含 BlueZ 的 `Device <MAC> <名称>` 和对应的 `Device` 属性变化事件。`Controller <MAC> Discovering: yes` 表示本机控制器正在扫描，不是附近设备；新版蓝牙 Agent 会过滤该行，并在启动时发布空设备数组覆盖旧版本的错误缓存。如果后台仍显示 `0E:00:73:33:C4:90`，应确认新版 `workcard-bluetooth-agent` 已经运行，并检查是否收到新的 `bluetooth/scan/reported` 消息。

正式蓝牙运行时必须同时存在 `/dev/ttyAMA1`、`hci_uart.ko`、`rtk_hciattach`、RTL8723D 固件、`S93bluetooth_audio`、`bluetoothd` 和 `bluealsad`。缺少 `hci0` 时设备没有执行真实扫描能力，耳机不会出现在结果中；此时后台已有列表只能视为历史数据。

## 云端 TLS 失败

检查系统时间、DNS、CA 文件权限、域名访问和证书有效期。Demo 禁止关闭 CA 或主机名校验。

## 后台显示离线

后台列表在线状态来自 MQTT retained Presence，不来自 WSS。确认 Demo 配置包含 `mqtt_host`、`mqtt_port=8883`、该设备专属 MQTT 用户名和密码，并检查：

```sh
tail -n 100 /tmp/workcard-demo.log
netstat -tnp | grep 8883
```

日志出现 `MQTT连接成功，设备在线状态已发布` 且 TCP 连接保持 `ESTABLISHED` 时，后台会在一个 Presence 保活周期内显示在线。

如果目标板解压精简包时出现 `Segmentation fault`，必须停止安装并检查归档是否只解出了部分目录；不得对不完整目录执行安装。重新上传后先校验 SHA-256 和归档目录，若目标板 BusyBox tar 仍然崩溃，应改用 SSH/SFTP 分文件传输并逐个校验，不能把部分解压结果当作正式安装结果。

## GNSS/IMU 返回不支持

这是第一版当前硬件的正式行为，不是故障。Air780EGP 串口和具体 IMU 型号接入后才会发布支持能力。
